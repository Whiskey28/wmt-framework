# 高可用系统升级规划

> 基于当前单体系统（Spring Boot + MySQL + Redis）的高可用升级方案
> 
> **当前状态**：单体应用，MySQL主从配置（可能未实际使用），Redis单节点，消息队列已配置但可能未完全使用

---

## 📋 规划总览

### 高可用目标
- **可用性**：99.9%+（年度停机时间 < 8.76小时）
- **容灾能力**：单点故障自动切换，数据零丢失
- **扩展性**：支持水平扩展，应对流量增长
- **监控告警**：全链路监控，故障快速发现与定位

### 升级原则
1. **渐进式升级**：优先解决单点故障，再逐步提升
2. **成本可控**：优先使用成熟方案，避免过度设计
3. **向后兼容**：升级过程不影响现有功能
4. **可回滚**：每个阶段都可独立回滚

---

## 🗄️ 1. 数据库高可用（MySQL）

### 当前状态
- MySQL主从配置已存在，但可能未实际使用
- 使用Druid连接池，支持多数据源
- MyBatis-Plus作为ORM框架

### 升级方案

#### 1.1 主从复制高可用（推荐：第一阶段）
**目标**：实现读写分离，提升查询性能，主库故障可切换

**方案**：
- **主从架构**：1主 + 2从（至少1从）
- **读写分离**：写操作走主库，读操作走从库
- **故障切换**：主库故障时，手动或半自动切换到从库

**技术实现**：
- 使用 `dynamic-datasource-spring-boot-starter` 实现读写分离（已支持）
- 配置主从数据源，自动路由
- 监控主从延迟，设置阈值告警

**优点**：
- 成本低，利用现有配置
- 提升读性能
- 数据备份自动完成

**缺点**：
- 主库故障需要手动切换（RTO较长）
- 主从延迟可能影响一致性

**实施步骤**：
1. 配置MySQL主从复制（如果未配置）
2. 验证主从同步状态
3. 配置dynamic-datasource读写分离
4. 代码改造：区分读写操作
5. 监控主从延迟和同步状态

---

#### 1.2 MySQL主从 + MHA自动切换（推荐：第二阶段）
**目标**：主库故障自动切换，RTO < 5分钟

**方案**：
- **MHA（Master High Availability）**：自动故障检测和切换
- **VIP漂移**：应用无需修改连接地址
- **Binlog补偿**：确保数据不丢失

**技术实现**：
- 部署MHA Manager节点
- 配置VIP（Virtual IP）
- 应用连接VIP，MHA负责切换

**优点**：
- 自动故障切换，RTO短
- 数据零丢失（配合半同步复制）
- 对应用透明

**缺点**：
- 需要额外服务器部署MHA
- 配置相对复杂

---

#### 1.3 MySQL集群方案（可选：第三阶段）
**目标**：更高可用性，支持多主或分库分表

**方案选择**：
- **MGR（MySQL Group Replication）**：MySQL官方方案，支持多主
- **Galera Cluster**：同步多主复制
- **分库分表**：ShardingSphere-JDBC（如需水平扩展）

**适用场景**：
- 需要多主写入
- 数据量巨大，需要分库分表
- 对一致性要求极高

---

### 数据库连接池优化
**当前**：Druid连接池，配置较基础

**优化项**：
- 增加连接池监控和告警
- 配置连接泄漏检测
- 优化连接池大小（根据实际QPS）
- 配置慢SQL告警和自动kill

## 🔴 2. Redis高可用

### 当前状态
- Redis单节点，存在单点故障风险
- 使用Redisson客户端
- 主要用于缓存、分布式锁、Session存储

### 升级方案

#### 2.1 Redis主从 + Sentinel哨兵（推荐：第一阶段）
**目标**：主节点故障自动切换，RTO < 30秒

**方案**：
- **架构**：1主 + 2从 + 3哨兵（Sentinel）
- **自动故障转移**：哨兵监控主节点，故障时自动切换
- **客户端适配**：Redisson支持Sentinel模式

**技术实现**：
- 部署Redis主从节点（1主2从）
- 部署3个Sentinel节点（奇数个，避免脑裂）
- 配置Redisson连接Sentinel地址
- 监控Sentinel状态和切换事件

**优点**：
- 自动故障切换，高可用
- Redisson原生支持，无需大改代码
- 成本可控（3台服务器）

**缺点**：
- 主从异步复制，可能丢失少量数据
- 切换期间可能有短暂不可用

**实施步骤**：
1. 部署Redis主从节点
2. 部署Sentinel节点
3. 配置Sentinel监控规则
4. 修改Redisson配置连接Sentinel
5. 测试故障切换流程
6. 配置监控告警

---

#### 2.2 Redis Cluster集群（推荐：第二阶段）
**目标**：支持水平扩展，数据分片存储

**方案**：
- **架构**：至少6节点（3主3从），支持水平扩展
- **数据分片**：使用CRC16算法分16384个slot
- **自动故障转移**：主节点故障，从节点自动提升

**技术实现**：
- 部署Redis Cluster（至少6节点）
- Redisson支持Cluster模式
- 配置集群监控和告警

**优点**：
- 支持水平扩展，性能线性提升
- 数据分片，单节点压力降低
- 自动故障转移

**缺点**：
- 需要更多服务器资源
- 跨slot操作不支持（如多key操作）
- 配置相对复杂

**适用场景**：
- Redis数据量大（>10GB）
- QPS高（>10万）
- 需要水平扩展

---

#### 2.3 Redis持久化优化
**当前**：可能使用RDB或AOF

**优化项**：
- **AOF + RDB混合**：兼顾性能和数据安全
- **AOF重写**：定期压缩AOF文件
- **持久化监控**：监控RDB/AOF执行时间和大小

## 📨 3. 消息队列高可用

### 当前状态
- 已配置RocketMQ、RabbitMQ、Kafka，但可能未完全使用
- WebSocket消息发送支持多种MQ

### 升级方案

#### 3.1 RocketMQ高可用（推荐：如果使用RocketMQ）
**目标**：Broker故障自动切换，消息不丢失

**方案**：
- **架构**：2主2从（双主双从模式）
- **NameServer集群**：至少2个NameServer节点
- **Broker集群**：主从自动切换，支持同步/异步复制

**技术实现**：
- 部署NameServer集群（2-3个节点）
- 部署Broker集群（2主2从）
- 配置同步刷盘和同步复制（保证数据不丢失）
- 客户端配置多个NameServer地址

**优点**：
- 自动故障转移
- 支持顺序消息、事务消息
- 消息不丢失（同步复制）

**缺点**：
- 需要较多服务器资源
- 配置相对复杂

---

#### 3.2 RabbitMQ高可用（推荐：如果使用RabbitMQ）
**目标**：节点故障自动切换，消息不丢失

**方案**：
- **镜像队列（Mirrored Queues）**：队列在多个节点镜像
- **集群模式**：至少3个节点（避免脑裂）
- **持久化**：消息和队列持久化到磁盘

**技术实现**：
- 部署RabbitMQ集群（3个节点）
- 配置镜像队列策略
- 启用消息持久化
- 配置HA策略（ha-mode: all 或 ha-nodes）

**优点**：
- 配置相对简单
- 自动故障转移
- 消息不丢失（持久化+镜像）

**缺点**：
- 镜像队列会复制所有消息，内存占用高
- 性能略低于RocketMQ

---

#### 3.3 Kafka高可用（推荐：如果使用Kafka）
**目标**：Broker故障自动切换，支持高吞吐

**方案**：
- **Broker集群**：至少3个Broker节点
- **副本机制**：Topic设置replication-factor >= 2
- **ISR机制**：In-Sync Replicas保证数据一致性

**技术实现**：
- 部署Kafka集群（3个Broker）
- 配置ZooKeeper集群（3个节点，Kafka依赖ZK）
- 创建Topic时设置副本数 >= 2
- 配置min.insync.replicas保证数据安全

**优点**：
- 高吞吐量，适合大数据场景
- 支持分区和水平扩展
- 自动故障转移

**缺点**：
- 需要ZooKeeper（Kafka 2.8+可用KRaft模式去除ZK）
- 配置相对复杂

---

### 消息队列选择建议
**根据业务场景选择**：
- **RocketMQ**：金融场景，需要事务消息、顺序消息
- **RabbitMQ**：中小型系统，配置简单，功能丰富
- **Kafka**：大数据、日志收集、高吞吐场景

**如果当前未大规模使用MQ，建议**：
- 先选择一种MQ深入使用（推荐RocketMQ或RabbitMQ）
- 统一消息发送和消费规范
- 逐步将异步任务迁移到MQ

## 🖥️ 4. 应用层高可用

### 当前状态
- Spring Boot单体应用
- 单实例部署，存在单点故障

### 升级方案

#### 4.1 应用多实例 + 负载均衡（推荐：第一阶段）
**目标**：消除单点故障，支持水平扩展

**方案**：
- **多实例部署**：至少2个应用实例
- **负载均衡**：Nginx/HAProxy/F5等
- **Session共享**：使用Redis存储Session（Spring Session）

**技术实现**：
- 部署2+个应用实例（不同服务器或容器）
- 配置Nginx负载均衡（轮询/加权轮询/IP Hash）
- 配置健康检查，自动剔除故障节点
- 使用Spring Session Redis实现Session共享

**优点**：
- 消除单点故障
- 支持水平扩展
- 配置相对简单

**缺点**：
- 需要负载均衡设备
- 需要解决Session共享问题

**实施步骤**：
1. 部署多个应用实例
2. 配置Nginx负载均衡
3. 配置健康检查
4. 集成Spring Session Redis
5. 测试故障切换

---

#### 4.2 服务注册发现（可选：第二阶段）
**目标**：动态服务发现，自动负载均衡

**方案选择**：
- **Nacos**：阿里开源，配置中心+注册中心
- **Consul**：HashiCorp开源，服务发现+配置中心
- **Eureka**：Spring Cloud Netflix（已停止维护，不推荐）

**技术实现**：
- 部署Nacos集群（3个节点）
- 应用集成Nacos Client
- 使用Spring Cloud LoadBalancer或Ribbon做负载均衡
- 配置健康检查和自动剔除

**优点**：
- 动态服务发现
- 支持配置中心
- 自动故障剔除

**缺点**：
- 需要额外基础设施
- 增加系统复杂度

**适用场景**：
- 微服务架构（未来可能拆分）
- 需要动态配置管理
- 服务实例频繁变化

---

#### 4.3 应用限流和熔断
**目标**：保护系统，防止雪崩

**方案**：
- **限流**：使用Sentinel或Resilience4j
- **熔断**：接口故障率超过阈值自动熔断
- **降级**：返回默认值或缓存数据

**技术实现**：
- 集成Sentinel（推荐，功能强大）
- 配置限流规则（QPS/并发数）
- 配置熔断规则（错误率/响应时间）
- 配置降级策略

**优点**：
- 保护系统稳定性
- 防止雪崩效应
- 提升用户体验

- 确保多个应用实例使用同一个数据库
- 配置instanceId为AUTO（自动生成）
- 监控qrtz_locks表，确保无死锁
- 配置任务执行监控和告警

## ⚠️ 风险和注意事项

### 风险1：数据一致性
- **风险**：主从延迟导致数据不一致
- **应对**：关键操作强制读主库，监控主从延迟

### 风险2：切换时间
- **风险**：故障切换期间服务不可用
- **应对**：优化切换流程，使用VIP减少切换时间

### 风险3：复杂度增加
- **风险**：系统复杂度提升，运维难度增加
- **应对**：完善文档和SOP，加强团队培训

### 风险4：成本增加
- **风险**：服务器和人力成本增加
- **应对**：分阶段实施，根据业务需求调整
