Chapter 1

是什么

ProGuard 是 Java 字节码处理工具，在 class 文件 层面工作，不读 .java 源码。

📥

输入

你们打好的 *.jar（program jar）+ JDK jmods + Maven 依赖（library jars，如 Spring）。

⚙️

处理

按 *.conf 规则做 shrink / optimize / obfuscate / preverify 四步（本仓库关闭了前两步）。

📤

输出

同名 JAR 覆盖原产物 + 内部 proguard_map.txt（映射表，禁止外发）。

ProGuard 经典四步 · 本仓库实际启用情况

1. Shrink

删除未引用类/成员
本仓库：关闭
-dontshrink

→

2. Optimize

内联、合并字节码
本仓库：关闭
-dontoptimize

→

3. Obfuscate

重命名 + 剥离调试信息
本仓库：启用

→

4. Preverify

写入 StackMap
JDK17 必须保留

关键概念：Program vs Library

Program classes（你们 JAR 里的类）可以被混淆。
Library classes（Spring、JDK 等依赖）只用来分析引用关系，不会被改写，也不会打进你们的 JAR。 本仓库通过 includeDependency=true 把 provided 依赖当作 libraryjars。

Chapter 2

为什么

wmt-framework 是被依赖的组件库，不是独立 App——策略必须「保运行、保 API、增逆向成本」。

🎯

保护什么

内部实现细节、工具类 private 成员、调试元数据。降低 jadx 一键还原源码的可读性。

🚫

不能破坏什么

Spring 自动配置类名、@ConfigurationProperties 字段、MyBatis Mapper、Validator、Jackson 序列化器——都靠反射或类名加载。

⚖️

为何不全量混淆

Starter 若 shrink + 重命名 core.**，业务系统启动即失败。库模块也禁止 shrink，避免误删「看起来未引用、运行期才用到」的类。

与 Android App 混淆的区别

Android 应用是封闭入口，ProGuard 可以激进 shrink。Spring Boot Starter 是开放插件， 被 Spring、MyBatis、Hibernate Validator 等多框架扫描——必须大量 -keep，混淆强度天然低于 App。

Chapter 3

怎么做

在本仓库，混淆是 Maven package 阶段自动执行的一步，由 Profile 开关控制。

~/.m2 或私服
业务方依赖

  1. 规则文件分层

    proguard-jdk17-library.conf → wmt-common；
    proguard-jdk17-starter.conf → 16 个 starter（include library 规则 + Spring/MyBatis keep）。
    路径：docs/proguard/，由根 pom.xml 的 proguard.config 引用。

  2. 插件挂载

    wmt-framework-jdk17/pom.xml 的 proguard-jar-modules profile：凡含 src/main/java 的子模块自动挂载 proguard-maven-plugin，默认 skip.proguard=true，加 -Pobfuscate 才执行。

  3. JDK 引导库

    ProGuard 需要 JDK 17 的 jmods/*.jmod 作 classpath 分析。 默认 proguard.jdk.home=${java.home}；也可 export PROGUARD_JDK_HOME=... 覆盖。

  4. 产物与保密

    发布：target/*.jar（已混淆）。
    内部留存：proguard_map.txt、proguard_seed.txt——勿提交 Git、勿发给业务方。

常用命令

export JAVA_HOME="$(/usr/libexec/java_home -v 17)"

# 先装 BOM（切换分支后建议删 .flattened-pom.xml 再 install）
mvn -f wmt-dependencies-jdk17/pom.xml clean install -DskipTests

# 全量 17 模块混淆安装
mvn -f wmt-framework-jdk17/pom.xml clean install -Pobfuscate -DskipTests

# 加强版规则链（当前与默认等价，预留收紧 keep）
mvn -f wmt-framework-jdk17/pom.xml clean install -Pobfuscate-strong -DskipTests

Chapter 4

三方视角

同一份组件，三个人看到的是三个世界。

① 框架维护者

Git 仓库里的你们
看到：
  • 完整 .java 源码、注释、芋道式包结构
  • docs/proguard/*.conf 规则与 README
  • 构建日志、proguard_map.txt 映射
  • *_proguard_base.jar 混淆前备份
职责： 维护 -keep 规则、验证 17 模块全量构建、决定是否收紧混淆。

② 业务依赖方

引入 starter 的应用团队
看到：
  • Maven 坐标不变：com.wmt:wmt-spring-boot-starter-web
  • IDE 补全：CommonResult、PageParam 类名方法名正常
  • application.yml 里 wmt.* 配置项名称不变
  • 运行时 JSON、异常格式与明文版一致
通常不会： 反编译框架 JAR；也不应收到 proguard_map.txt。

③ 逆向分析者

拿到 ~/.m2 里 JAR 的人
看到：
  • public API 类名仍在（CommonResult、WmtWebAutoConfiguration）
  • 无 SourceFile / LineNumberTable，jadx 难对应 .java 行
  • package-info 等变成 a.class
  • 部分 private 字段、lambda 名为 a、b
若拿到 map： 混淆基本失效——故 map 必须内控。
维护者 · 磁盘上的文件
wmt-framework-jdk17/wmt-common/src/main/java/.../CommonResult.java docs/proguard/proguard-jdk17-library.conf wmt-common/target/proguard_map.txt ← 内部 wmt-common/target/*_proguard_base.jar ← 可删
依赖方 · ~/.m2 里只有一个
~/.m2/repository/com/wmt/wmt-common/.../ wmt-common-2025.12-jdk17-SNAPSHOT.jar ← 已混淆，即依赖产物 // pom.xml 与明文版完全相同 <artifactId>wmt-spring-boot-starter-web</artifactId>
Chapter 5

典型案例

每个案例标注「是什么 / 为什么 / 怎么做」，左为仓库真实形态，右为依赖方或 JAR 内形态。

1

统一返回体 CommonResult

是什么 保 API

是什么：业务 Controller 统一返回的 JSON 包装类。为什么 keep：common.pojo.** 被业务代码直接 import。怎么做：library.conf 整包 -keep { *; }。

维护者 · CommonResult.java
public class CommonResult<T> { private Integer code; private String msg; private T data; public static <T> CommonResult<T> success(T data) { ... } public static <T> CommonResult<T> error(Integer code, String msg) { ... } }
依赖方 · 写法与 javap 签名
// 业务代码（完全不变） return CommonResult.success(vo); // javap 混淆 JAR public class ...CommonResult { public static CommonResult success(Object); public Integer getCode(); public String getMsg(); }
2

Spring Boot 自动配置

保类名 SPI 加载

是什么：META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 列出配置类全名。为什么：Spring 按字符串 loadClass，类名变则启动失败。怎么做：starter.conf keep @AutoConfiguration 与 config.**。

维护者 · imports 文件
META-INF/spring/...AutoConfiguration.imports com.wmt.framework.web.config.WmtWebAutoConfiguration com.wmt.framework.jackson.config.WmtJacksonAutoConfiguration com.wmt.framework.swagger.config.WmtSwaggerAutoConfiguration ...
依赖方 · 引入 starter 即生效
// 业务 pom 只需依赖，无需 @Import <artifactId>wmt-spring-boot-starter-web</artifactId> ✓ 混淆前后 imports 内容一致 ✓ Filter / ExceptionHandler 类名保留 ✓ 业务无感知
3

工具类 PageUtils 的 private 成员

混淆内部 public keep

是什么：分页辅助工具。为什么部分混淆：util.** 只 keep public 方法，private 与 lambda 可缩短。怎么做：业务只调 PageUtils.getStart()，签名不变。

维护者 · 源码 + map
public class PageUtils { public static int getStart(PageParam p) { ... } private static Integer cacheMax = 1000; } // proguard_map.txt（内部） cacheMax → a lambda$xxx → b
依赖方 · 只用到 public
PageUtils.getStart(pageParam) IDE 提示正常 PageParam.getPageNo() 正常 // 依赖方不会、也不应访问 private // 逆向者看到 a、b 但无源文件行号
4

全局异常 GlobalExceptionHandler

保运行 元数据剥离

是什么：将异常转为 CommonResult JSON。为什么类名保留：core.** 整包 keep。怎么做：剥离 SourceFile/LineNumberTable，反编译可读性下降，运行时行为不变。

维护者 · javap 明文 class
Compiled from "GlobalExceptionHandler.java" SourceFile: "GlobalExceptionHandler.java" LineNumberTable: line 42: 0 line 43: 5 ...
依赖方运行时 + 逆向者 javap
// 业务抛 ServiceException { "code": 400, "msg": "xxx", "data": null } 不变 // 混淆后 javap public class ...GlobalExceptionHandler { ... } （无 Compiled from / SourceFile / LineNumberTable）
5

校验注解 @Mobile / ConstraintValidator

反射加载

是什么：Hibernate Validator 按类名实例化校验器。为什么全 keep：@Constraint 与 validation.** 规则。怎么做：业务 DTO 照常写注解，校验失败仍走统一异常响应。

依赖方 · DTO
public class UserCreateReqDTO { @Mobile private String mobile; }
混淆 JAR 内
MobileValidator 类名保留 @Mobile 注解保留 校验失败 → CommonResult 400 // 若混淆 Validator 类名 → 运行期 ClassNotFound
6

若错误开启 shrink（反面教材）

为何 -dontshrink

是什么：删除「静态分析认为未使用」的类。为什么危险：Spring 反射加载、MyBatis 接口代理在分析期不可见。怎么做：library + starter 均 -dontshrink -dontoptimize，用 keep 精确控制而非删类。

假设去掉 -dontshrink 后
✗ AutoConfiguration 类被删 → 自动配置不生效 ✗ TypeHandler 被删 → 数据库类型映射失败 ✗ ConstraintValidator 被删 → 校验静默失效 // 业务表现：启动成功但功能残缺，最难排查
本仓库做法
-dontshrink -dontoptimize 大量 -keep 保留框架契约 仅 obfuscate + 元数据剥离 // 牺牲「最小体积」，换取「可预测的启动」
