### 一、平台覆盖与使用情况类

#### 1. DevOps 覆盖项目占比

- **核心口径**：  
  - 分母：公司全部在管项目数  
  - 分子：年度内在 DevOps 有“流水线 / 代码提交 / 特性/需求记录”的项目数
- **推荐来源**：
  - “平台项目”：`yanlian_devops_development`  
    - `devops_project`（或等价表，代表项目维度，字段一般有 `id`, `project_name`, `tenant_id` 等）
  - “有实际使用痕迹”的判定：
    - 代码：`yanlian_devops_scm` → 仓库或 `project_commit_relation`、`commit_info.project_id`
    - 流水线：`yanlian_dop_pipeline` → `devops_job_build_info.project_id`
    - 需求/特性：`yanlian_devops_development` → `devops_feature.feature_project_id`
- **统计逻辑**：
  - 分母：当年存在的全部 DevOps 项目 `COUNT(DISTINCT devops_project.id)`
  - 分子：当年在上面任一“使用痕迹”表里出现过的 `project_id` 去重

#### 2. DevOps 覆盖部门占比

- **来源**：
  - 组织：`yanlian_app_management` → `sys_organization`（`id`, `name`, `is_deleted`, `status`）
  - 项目/系统归属：
    - 项目：`devops_project.tenant_id`（= 组织 id）
    - 系统：`devops_system.tenant_id` 或类似字段（在 `yanlian_devops_development` 里）
- **统计逻辑**：
  - 分母：在职、未删除的组织数 `COUNT(DISTINCT sys_organization.id WHERE is_deleted=0)`
  - 分子：有项目/系统接入 DevOps 的组织数 `COUNT(DISTINCT tenant_id)`  
  - 可做 **Top3 部门**：按“本部门活跃项目数 / 部署次数”等排前三。

#### 3. 平台年度活跃用户 / 公司用户占比

- **来源**：
  - 用户：`yanlian_app_management` 中用户表（一般是 `sys_user` 或类似）
  - 平台行为：
    - 提交：`yanlian_devops_scm` → `commit_info.author_id`
    - 构建/部署：`yanlian_dop_pipeline` → `devops_job_build_info.trigger_user` / `devops_build_deploy_rel` 中触发人字段（若有）
    - 需求/特性：`yanlian_devops_development` → `devops_feature.create_by`/`director`
    - 知识：`yanlian_devops_knowledge` → `knowledge_document.user_id`、`knowledge_comment.user_id`
- **统计逻辑**：
  - 分母：在职用户数（按 `sys_user.status` + 非删除）
  - 分子：上述行为表中出现过的 `user_id` 去重

#### 4. 平台活跃天数占比（热力日历）

- **来源**：同上所有“行为表”的 `create_time`/执行时间
- **逻辑**：
  - 一年 365 天中，统计有任意一条行为记录的天数 ÷ 365  
  - 热力日历：按天计数（不展示具体数，仅高低对比）

### 二、交付效率 / DORA 风格

#### 5. 部署频率提升倍数（今年 vs 去年）

- **来源**：`yanlian_dop_pipeline` → `devops_build_deploy_rel`
  - 字段：`start_time`（时间）、`status`、`deploy_env`、`job_id`, `build_id`
- **逻辑**：
  - 按周统计 `status='SUCCESS'` 的记录数  
  - 今年每周平均值 ÷ 去年每周平均值  
  - Top3：可按“部署次数最多的项目/系统”排名（需要 join job/build 对应的系统/项目字段）

#### 6. 平均交付周期缩短比例（Lead Time）

- **来源**：
  - 需求/特性：`yanlian_devops_development` → `devops_feature`
    - `id`, `feature_name`, `feature_project_id`, `create_time`, `feature_status`
  - 上线部署：`yanlian_dop_pipeline` → `devops_build_deploy_rel`
    - 找“生产环境”成功部署（需要约定哪个 `deploy_env` 为生产）
- **技术友好口径**：
  - 为每个 `devops_feature` 找到该特性在流水线中的“首次生产成功部署时间”（可通过关联 feature 相关的分支/版本到 `build_id` / job）  
  - Lead Time = `first_prod_success_time - create_time`
  - 对比今年与去年的平均 Lead Time，算缩短比例

#### 7. 自动化流水线覆盖率

- **来源**：
  - 全部有上线记录的系统/项目：  
    - 生产部署：`devops_build_deploy_rel` 中生产 env 的记录，关联系统/项目
  - 有流水线记录：`devops_jenkins_job` + `devops_job_build_info`
- **逻辑**：
  - 分母：当年有生产部署记录的系统/项目数
  - 分子：这些系统/项目中，有对应 `devops_jenkins_job` 且在 `devops_job_build_info` 有执行记录的数量

#### 8. 标准化发布占比（一键部署占比）

- **来源**：
  - `devops_build_deploy_rel` + `devops_jenkins_job`
    - 可通过 job 的 `template` / `job_type` / 名称约定来识别“标准化流水线”
- **逻辑**：
  - 分子：归类为标准化流水线的部署（成功+失败都算）次数
  - 分母：所有部署次数

### 三、质量与代码健康

#### 9. 代码扫描接入覆盖率

- **来源**：`yanlian_devops_code_inspect`
  - 仓库：`code_repository`（`id`, `project_id`, `repo_name`...）
  - 扫描历史：`scan_history`（`repository_id`, `scan_time`）
- **逻辑**：
  - 分母：在管代码仓库总数 `COUNT(DISTINCT code_repository.id)`
  - 分子：本年度有 `scan_history` 记录的 `repository_id` 数量

#### 10. 质量红线通过率（静态扫描 Gate）

- **来源**：
  - `scan_history`（含每次扫描结果，字段如 `status`、`quality_gate_status`）
  - `quality_gate`（质量门禁配置）
- **逻辑**：
  - 分母：触发了质量 Gate 的 `scan_history` 次数（`quality_gate_id` 不为 NULL）
  - 分子：这些记录中 `quality_gate_status='PASS'` 的次数

#### 11. 问题闭环率（质量问题处理）

- **来源**：
  - `scan_issue`（或 `scan_history_detail` + 问题聚合）
    - 字段：`status`（open/fixed/closed 等）、`created_time`, `resolved_time`
- **逻辑**：
  - 本年度“新产生的问题”：`created_time` 在本年度  
  - “已闭环”：`status in ('fixed','closed',...)`，或 `resolved_time` 在本年度  
  - 闭环率 = 已闭环问题 ÷ 本年度产生的问题

#### 12. 代码质量改善指数（示意）

- **来源**：
  - `scan_history` + `scan_issue`  
  - 每次扫描时的问题总数 / 严重度分布
- **逻辑**（友好型）：
  - 按月：计算“每次扫描平均严重问题数/一般问题数”，与年初做对比，用归一化方式转成 0–100 分的指数  
  - 指数上升说明质量改善

### 四、安全与依赖可信

#### 13. 可信扫描覆盖应用占比

- **来源**：`yanlian_devops_trustworthy`
  - 应用：`devops_app`（`id`, `app_name`, `tenant_id`, ...）
  - 扫描历史：`devops_app_scan_history`（`app_id`, `scan_time`）
- **逻辑**：
  - 分母：本年度有上线记录的应用数（可从部署记录或 `devops_app` 状态判断）
  - 分子：这些应用中，本年度有 `devops_app_scan_history` 的应用数

#### 14. 安全门禁通过率

- **来源**：
  - `devops_security_gate`（门禁配置）、`devops_gate_app_relation`（门禁应用关系）
  - 具体触发和结果可能也记录在 `devops_app_scan_history` 或单独“gate执行记录表”
- **逻辑**：
  - 统计本年度触发安全 Gate 的次数中，处于“通过/满足条件”的比例

#### 15. 高危问题处理率

- **来源**：
  - 漏洞：`devops_leak`（严重级别），`devops_leak_dp_relation`（漏洞与依赖关系），`devops_dependency` / `devops_dependency_detail`
- **逻辑**：
  - 本年度新发现高危（严重等级为 HIGH/CRITICAL）的漏洞数  
  - 本年度内被标记为“已修复/已关闭”的高危漏洞数  
  - 处理率 = 修复数 ÷ 发现数  
  - 可加 Top3：按“高危漏洞处理率最高/最低”的项目或应用名

### 五、知识与协同

#### 16. DevOps 知识空间接入项目占比

- **来源**：`yanlian_devops_knowledge`
  - 空间：`knowledge_space`（`id`, `project_id`, `name`）
- **逻辑**：
  - 分母：DevOps 平台项目总数（`devops_project`）
  - 分子：`knowledge_space.project_id` 非空且映射到现有 DevOps 项目的数量

#### 17. 项目文档完备度

- **来源**：
  - 文档：`knowledge_document`（`space_id`, `name`, `file_type` 等）
  - 模板/类型：`knowledge_template` + `document_id` 或根据 `name` 关键字（如包含“接口文档”“设计说明”等）
- **逻辑**：
  - 为每个项目，判断是否拥有“关键文档类型集合”（至少 README、架构说明、接口文档）  
  - 完备项目数 ÷ 有知识空间的项目数  
  - Top3：文档最完备、更新最频繁的项目

#### 18. 知识参与度（评论/收藏参与）

- **来源**：
  - 评论：`knowledge_comment`（`document_id`, `user_id`, `create_time`）
  - 收藏：`knowledge_user_collect`（`document_id`, `user_id`）
- **逻辑**：
  - 有评论/收藏的文档数 ÷ 全部文档数  
  - 或参与评论/收藏的独立用户数 ÷ DevOps 活跃用户数

### 六、规范执行与工程实践

#### 19. 提交规范检查覆盖率

- **来源**：`yanlian_devops_scm`
  - 规则：`devops_commit_check_rule`（项目/仓库级别规则配置）
  - Git 仓库/项目：`project_commit_relation`、`devops_code_config_relation`
- **逻辑**：
  - 分母：有代码仓库的项目数  
  - 分子：配置了至少一条 commit check 规则并处于启用状态的项目/仓库数

#### 20. MR 审查通过率

- **来源**：
  - `devops_merge_request`（`id`, `project_id`, `status`, `created_time`）
- **逻辑**：
  - 本年度 MR 总数  
  - 状态为“merged/accepted”的 MR 数  
  - 通过率 = merged ÷ total  
  - Top3：MR 审查通过率最高/最低的项目（可只展示最高 + 平均）

#### 21. 标准流水线模板使用率

- **来源**：
  - `devops_agent_template`（流水线/agent 模板）
  - `devops_jenkins_job` 中引用模板的字段（如 `template_id`）
  - `devops_job_build_info`（实际运行次数）
- **逻辑**：
  - 分母：所有流水线运行次数  
  - 分子：`template_id` 属于平台标准模板集合的运行次数

### 七、你特别提到的两个“排行榜”设计

#### A. 安全漏洞排行榜（问题最严重的项目/应用 Top3）

- **目标**：告诉大家“哪些系统/应用在安全和依赖方面问题最多，需要更多关注”（既起到提醒，也展示平台有能力“点名”）。
- **来源**：`yanlian_devops_trustworthy`
  - 应用：`devops_app`（`id`, `app_name`, `tenant_id`）
  - 漏洞：`devops_leak`（`id`, `severity`, `status`, `app_id` 或通过中间表关联）
  - 关系列表：`devops_leak_dp_relation`（将漏洞与依赖、应用关联）
- **排行榜维度建议**（可选 1–2 个）：
  - 按“当前未修复高危漏洞数量”排序的 Top3 应用/系统
  - 按“高危漏洞发现后平均处理时长”排序的 Top3（处理越慢越靠前）
- **注意“真实亲人”口径**：
  - 新闻稿文案可以写：  
    - “从平台数据看，X 应用和 Y 系统在高危漏洞暴露上相对集中，已经纳入专项治理。”  
    - 同时给“一年内高危漏洞处理率”的整体提升情况，避免只点问题不讲改进。

#### B. 代码质量命中排行榜（静态扫描问题最集中的 Top3 项目）

- **来源**：`yanlian_devops_code_inspect`
  - 仓库：`code_repository`（`id`, `project_id`, `repo_name`）
  - 扫描历史：`scan_history`（`id`, `repository_id`, `scan_time`）
  - 问题：`scan_issue`（`history_id`, `severity`, `type`, `rule_id`, `status`）
  - 规则：`rule_info`（`id`, `name`, `type`, `language`）
- **两个排行榜建议**：
  1. **项目质量问题 Top3**  
     - 指标：本年度每千行代码平均命中的严重+一般问题数量（若有代码行数字段；没有则直接用“每次扫描平均严重问题数”代替）  
     - 排名对象：项目 / 仓库（展示真实项目名）  
     - 用法：结合“问题闭环率”一起展示，避免负面解读。
  2. **问题类型命中 Top3（知识性科普）**  
     - 指标：按 `rule_info` 或问题类型统计在全平台的命中次数，比如“空指针风险”、“SQL 注入潜在风险”、“魔法值”等  
     - 排名对象：规则/问题类型，而不是项目  
     - 这块非常适合新闻稿中做“科普”：  
       - “从静态扫描结果看，开发过程中最容易忽视的是 X、Y、Z 三类问题，平台通过规则自动提示和阻断。”
